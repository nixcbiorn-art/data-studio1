# RedCat Studio

Приложение для сбора, поиска, анализа и правки данных из любого REST API.
Изначально сделано под redcat.ai, но к нему не привязано: источники
описываются JSON-файлами, программировать для подключения нового API не нужно.

---

## 🔒 Главное: в API уходят только GET-запросы

Приложение **физически не может** изменить что-либо на стороне API.
Это не договорённость и не обещание, а блокировка в коде.

Модуль `api_guard.py` подменяет точки входа `requests` и `aiohttp`. Любой
вызов с методом, кроме `GET`, `HEAD` и `OPTIONS`, падает с исключением
**до открытия сетевого соединения** — запрос не уходит в сеть вообще.
Под блокировкой находятся и сборщик, и приложение, и запуски по расписанию.

Проверить самому — двойной клик по **`check_readonly.bat`** (или
`python selftest_readonly.py`). Скрипт пытается отправить PUT, POST, PATCH и
DELETE всеми способами, которыми это вообще делается в проекте, и показывает,
что каждый из них заблокирован:

```
✅ session.request(PUT)     ЗАБЛОКИРОВАНО
✅ requests.post()          ЗАБЛОКИРОВАНО
✅ aiohttp PATCH            ЗАБЛОКИРОВАНО
✅ requests.delete()        ЗАБЛОКИРОВАНО
```

Дополнительно ведётся журнал **всех** исходящих запросов — метод, адрес,
HTTP-код, время ответа. Он виден в приложении на вкладке «Журнал API».
То есть режим «только чтение» не только гарантирован заранее, но и
проверяем постфактум.

**Тогда как же «редактирование»?** Правки применяются к вашей локальной копии
данных и хранятся отдельным файлом `studio.db`. Список правок выгружается в
CSV/JSON — его можно передать тому, кто вносит изменения в первоисточник.
Подробнее — в разделе «Правка данных».

## Быстрый старт

1. **Посмотреть приложение прямо сейчас**, без токена и без установки
   библиотек: двойной клик по `demo_data.bat`, затем по `studio.bat`.
   Создастся набор выдуманных данных, и приложение откроется в браузере.

2. **Работа с настоящими данными:**
   ```
   pip install -r requirements.txt
   ```
   Затем `studio.bat` → вкладка «Сбор» → вставить токен → «Запустить сбор».

Самому приложению никакие библиотеки не нужны: оно собрано на стандартной
библиотеке Python и работает офлайн. Зависимости из `requirements.txt`
требуются только для похода в API и записи Parquet/Excel. Если их нет,
приложение честно скажет, чего не хватает, и всё равно откроет уже собранные
данные.

Не Windows? Те же команды без `.bat`:
`python demo_data.py`, `python studio.py`, `python selftest_readonly.py`.

## Что умеет приложение

Открывается по адресу `http://127.0.0.1:8765/`. Сервер слушает только
localhost, то есть в сеть не смотрит и с другого компьютера недоступен.

### 📊 Обзор
KPI по последнему запуску с дельтой к предыдущему, графики динамики (объём,
цены, цена за м², оборот лотов, полнота сбора, длительность), список таблиц и
свежих файлов выгрузки.

### 🗃️ Данные
- Таблица с сортировкой по любой колонке, постраничным выводом и выбором
  видимых колонок.
- **Конструктор фильтров**: 16 операторов (равно, больше, в диапазоне,
  содержит, начинается с, пусто, один из, регулярное выражение…), объединение
  по «И» либо «ИЛИ».
- **Быстрые срезы** — частые значения любой колонки с количествами; клик
  добавляет фильтр.
- **Правка ячейки двойным кликом**, массовая правка по текущему фильтру,
  избранное, скрытие записей, заметки и теги.
- **Колонки-формулы**: своя колонка вида `price / total_area`, считается на лету.
- **Сохранённые виды** — фильтр, сортировка и набор колонок под именем.
- Выгрузка текущей выборки в CSV или JSON.
- Карточка записи: все поля, история правок, график значения по запускам.

### 🔍 Поиск
Полнотекстовый поиск сразу по всем таблицам (SQLite FTS5). Слова ищутся по
началу: «солне» находит «Солнечный». Результат ведёт прямо в карточку записи.

### 📈 Аналитика
Десять инструментов, все учитывают фильтры со вкладки «Данные»:

| Инструмент | Что отвечает |
|---|---|
| **Сводная** | количество / сумма / среднее / медиана / перцентили в разрезе поля |
| **Сводка по группам** | все метрики сразу по каждой группе: разброс, квартили, края |
| **Таблица × таблица** | пересечение двух разрезов (застройщик × тип отделки) |
| **Динамика по дате** | как распределены записи по их собственной дате: по дням, неделям, месяцам, годам |
| **Связь полей** | коэффициент Пирсона и облако точек с линией тренда |
| **Парето (ABC)** | какая часть групп даёт 80% объёма |
| **Распределение** | гистограмма числового поля — видны перекосы и хвосты |
| **Топ / антитоп** | края распределения с подписями |
| **Выбросы** | по медиане и MAD, в том числе внутри групп |
| **Дубликаты** | одинаковые ключи и сколько строк лишние |

Две оговорки, которые приложение проговаривает прямо в интерфейсе:

- **Выбросы считаются по медиане и MAD, а не по среднему и σ.** Одно
  экстремальное значение сдвигает среднее так, что настоящие выбросы
  перестают выделяться на его фоне. Разрез по группам ловит «дешёвый лот в
  дорогом ЖК», незаметный в общем распределении.
- **Связь — это не причина.** Высокий коэффициент корреляции означает, что
  величины меняются согласованно, и ничего не говорит о том, что одна влияет
  на другую: совпадение часто объясняется третьим фактором, которого в этих
  двух колонках нет.

### 🧪 Качество
Профиль каждой колонки: заполненность, уникальность, минимум, медиана,
максимум. Плюс накопленный список аномалий с фильтром по важности. Низкая
заполненность важного поля — повод не доверять расчётам по нему.

### 🔄 Изменения
Что появилось, что пропало и какие поля изменились относительно прошлого
запуска, с поиском и фильтром по категории.

### ✏️ Мои правки
Все локальные правки одним списком: было → стало, когда, у какой записи.
Откат по одной или целиком. Выгрузка в CSV/JSON.

### 📡 Сбор
Токен с индикатором срока действия, выбор источников, параллельность,
запуск и остановка, живой лог прямо в окне.

### 🔌 Источники
Список подключённых API, редактор описания, удаление, сбор одного источника.
**Проверка эндпоинта**: один GET-запрос — и приложение само предлагает готовое
описание источника (где массив записей, где общее число, где ссылка на
следующую страницу, что похоже на идентификатор и название).

### ⌨️ SQL
Консоль с деревом схемы. Разрешены только `SELECT` и `WITH`; защит три и они
независимы — соединение открыто в режиме только для чтения, допускается один
запрос, и он обязан начинаться с SELECT/WITH. Результат выгружается в CSV.

### 🔒 Журнал API
Все обращения к стороннему API с методами и кодами ответа. Если в списке
когда-нибудь появится PUT или DELETE, он будет помечен как заблокированный —
сам запрос в сеть не уйдёт.

## Правка данных: как это устроено

Правки **не отправляются в API** — это невозможно технически. Они пишутся
в отдельную базу `studio.db` и накладываются на данные при чтении.

Почему отдельная база, а не та же `redcat_data.db`: сборщик пересоздаёт свои
таблицы при каждом запуске (`if_exists="replace"`). Если бы правки лежали там
же, следующий сбор стирал бы их подчистую. Сейчас данные обновляются, а
правки остаются поверх.

Что сохраняется вместе с правкой: старое значение (поэтому всегда можно
откатить и всегда видно «было → стало»), время и автор. Отменённые правки не
удаляются, а гасятся — история остаётся.

Режимы массовой правки по текущему фильтру: установить значение, заменить
текст, заменить по регулярному выражению, убрать лишние пробелы, посчитать по
формуле.

## 🩺 Если собралось меньше, чем должно

**Первое, что стоит запустить:**

```
python redcat_scraper.py --diagnose
```

Проверка идёт по реальным запросам, но дёшево — несколько GET-ов на
источник вместо полного обхода. Она проходит всю цепочку, на каждом звене
которой данные теряются молча, и говорит, где именно рвётся:

1. URL собирается, все плейсхолдеры подставлены.
2. Запрос проходит, ответ — валидный JSON.
3. Массив записей лежит там, где указано в `data_path`.
4. Общее число записей находится (без него полноту не с чем сверять).
5. Есть ссылка на следующую страницу — и она абсолютная.
6. Страница 2 действительно отличается от страницы 1.
7. Размер страницы соблюдается сервером.
8. Для дробящихся источников — фильтр реально фильтрует.
9. Оценка: сколько страниц нужно и упрёмся ли в лимит окна пагинации.
10. Сверка с тем, что уже лежит в локальной базе.

Каждое замечание сопровождается конкретной подсказкой, что править
в `sources/*.json`.

### Если API отвечает HTTP 500 вместо понятной ошибки

Некоторые бэкенды не проверяют параметры заранее и падают с 500 там, где
аккуратный API вернул бы 400 — например, на незнакомом поле сортировки или
не том формате булева фильтра (`true` вместо `1`). Раньше в этом месте была
своя проблема: код вызывал `resp.raise_for_status()`, чьё сообщение — просто
«500 Server Error» без единого слова о причине, а настоящий текст ошибки
из тела ответа терялся и нигде не показывался.

Теперь тело ответа печатается всегда, а `--diagnose` при таком сбое
дополнительно **сам находит виновный параметр**: пробует запрос без каждого
фильтра по очереди (по одному дешёвому GET на параметр) и сообщает, без
какого именно запрос вдруг проходит:

```
❌ Без одного из параметров запрос проходит — вот виновник
    без «sort=created_at_desc» → HTTP 200 (успех)

Что делать:
    Вероятная причина — именно этот параметр:
        sort=created_at_desc
    Проверьте его написание и формат в документации API.
```

Ошибки заодно делятся на два вида: если в теле ответа есть след
необработанного исключения на сервере (SQL-ошибка, трассировка) — обход
не тратит время на бессмысленные повторы одного и того же сломанного
запроса и сразу сообщает об этом. Обычный временный сбой (просто
«Internal Server Error» без подробностей) по-прежнему повторяется с
паузой — такие чаще всего проходят со второй-третьей попытки.


### Что было починено в парсере

Три ошибки приводили к тихой потере данных — обход останавливался, а
сообщения об ошибке не было:

| Что было | Что происходило | Как стало |
|---|---|---|
| Относительная ссылка `links.next` (`/api/v2/...`) уходила в запрос как есть | `requests` падал с `MissingSchema`, обход обрывался **после первой страницы** | Ссылка достраивается до абсолютной относительно текущей |
| Нет `links.next` → обход считался законченным | Собиралась **только первая страница**, даже если `meta.total` говорил о десятках тысяч | Есть запасной путь: обход по номерам страниц, пока приходят полные страницы |
| `page[size]` в ссылке приходил URL-кодированным (`page%5Bsize%5D`) | Параметр не распознавался и дописывался второй раз — сервер брал какой хотел | Параметры сравниваются в раскодированном виде, дубликатов не возникает |

Добавлены и защиты от молчаливых потерь:

- **Общее число записей** ищется не только по `total_path`, но и по десятку
  типовых путей (`meta.total_count`, `meta.pagination.total`, `total`…).
  Раньше, если путь не совпадал, сверка полноты просто отключалась — и
  недостача оставалась незамеченной.
- **Застрявшая пагинация** распознаётся: если страница 2 повторяет страницу
  1, значит API не понимает параметр номера страницы. Обход
  останавливается с объяснением, а не крутится вечно, набивая дубликаты.
- **Лимит окна пагинации** объясняется текстом, а не остаётся безымянной
  HTTP 500.
- **Предпроверка дробления** стала настоящей. Раньше успехом считался любой
  HTTP 200 — и если фильтр молча игнорировался, обход собирал одну и ту же
  выдачу тысячи раз. Теперь сравнивается число записей с фильтром и без
  него: если совпадает, сбор останавливается с объяснением.
- **Недостача больше 20%** — это ошибка, а не примечание мелким шрифтом.
  Запуск помечается неполным, в консоль выводятся вероятные причины.

## 🩺 Сквозные проверки (вкладка «Проверки»)

Отвечают на вопрос «можно ли этими данными пользоваться». Отличие от поиска
аномалий: аномалии ищут необычное внутри одной таблицы, а здесь
проверяется, сходятся ли таблицы друг с другом. Такие поломки не выглядят
странно — просто цифры меньше, чем должны быть.

- **Полнота** — собрано против заявленного API числа.
- **Битые связи** — записи, ссылающиеся на отсутствующий справочник.
- **Покрытие** — сколько записей справочника вообще представлено в дочерней
  таблице. Много «пустых» ЖК — типичный след неполного сбора.
- **Дубликаты идентификаторов** — обычно след дробления по параметру,
  который API игнорирует.
- **Пустые обязательные поля** и **невозможные значения** (цена ≤ 0).
- **Рассогласование названий** одной сущности в разных таблицах.

Связи между таблицами определяются автоматически — по описаниям источников
и по именам колонок, — поэтому проверки работают и для источников, которые
вы добавили сами.

Там же, в карточке любой записи, появился переход по связям: из ЖК — в его
квартиры, регламенты и тарифы, из квартиры — обратно в ЖК. Кнопка «Показать
все» открывает нужную таблицу уже отфильтрованной.

## Токен

Берётся из `.env` рядом с приложением либо передаётся разово:

```
python redcat_scraper.py --token "eyJ...ваш_токен"
```

Разовый токен нигде не сохраняется. Если указаны и `--token`, и `.env` —
приоритет у `--token`. Обновить токен в `.env` можно из приложения (вкладка
«Сбор»), из панели `launcher.bat` или командой `python set_token.py "..."`.

Срок действия проверяется **до** похода в API, по полю `exp` внутри JWT:
истёкший токен даёт понятную ошибку сразу, а не HTTP 401 на сотом запросе.
Если до истечения меньше суток — предупреждение.

⚠️ Токен, который был вшит в исходный файл первой версии, считайте
скомпрометированным — перевыпустите его в личном кабинете.

## Автозапуск по будням в 10:00

Через Планировщик заданий Windows.

1. Убедитесь, что `python redcat_scraper.py` успешно отрабатывает вручную.
2. Запустите `install_scheduled_task.bat` **от имени администратора**, либо
   нажмите «Установить автозапуск» в панели `launcher.bat` — она сама
   запросит права через UAC.

Отменить — `uninstall_scheduled_task.bat`.

⚠️ **Про токен и автозапуск.** Токен выдаётся на сессию и истекает, а
у безлюдного запуска нет способа получить новый — он всегда берётся из `.env`.
Поэтому обновляйте `.env` заранее и поглядывайте в `run_log.txt`: скрипт
предупреждает там, если токену осталось меньше суток. Если токен всё же
истёк — запуск в этот день завершится ошибкой, ничего не сломается.

Требования: компьютер включён и не спит в 10:00 (либо в свойствах задачи,
вкладка «Условия», включите «будить компьютер для выполнения задачи»).

**macOS/Linux** — вместо Планировщика строка в `crontab -e`:

```
0 10 * * 1-5 cd /путь/к/redcat_scraper && /usr/bin/python3 redcat_scraper.py >> run_log.txt 2>&1
```

## Подключение нового API

### Из приложения (проще всего)

Вкладка «Источники» → «Проверка эндпоинта». Вставьте адрес, нажмите
«Проверить» — уйдёт один GET-запрос, и по ответу приложение само построит
черновик описания: где лежит массив записей, где общее число, где ссылка на
следующую страницу, какое поле похоже на идентификатор и на название, какие
поля числовые. Черновик можно поправить прямо там и сохранить.

### Вручную

Источник — это JSON-файл в папке `sources/`. Код трогать не нужно: сбор,
нормализация, пагинация, сравнение, метрики, аномалии, качество, выгрузка и
графики работают с любым источником одинаково.

Минимум:

```json
{ "key": "my_source", "url": "https://api.example.com/v1/items?org={org}" }
```

Плейсхолдеры берутся из `.env`: `{org}` ← `REDCAT_ORG`.

Если структура ответа другая — опишите её:

```json
{
  "key": "github_repos",
  "url": "https://api.example.com/v3/repos?org={org}",
  "data_path": ["items"],
  "next_link_path": ["pagination", "next_page"],
  "total_path": ["pagination", "total_count"],
  "page_size_param": "per_page",
  "page_number_param": "page",
  "mapping": { "id": "id", "name": "full_name", "owner": "owner.login", "stars": "stargazers_count" },
  "derived": { "stars_per_fork": "stars / forks" },
  "numeric_fields": ["stars", "forks"],
  "group_fields": ["owner"],
  "positive_fields": ["stars"]
}
```

Что произойдёт дальше само:

- в SQLite появится таблица `github_repos` с индексами, плюс Parquet-файл;
- в историю запусков добавятся колонки `github_repos_count`,
  `github_repos_stars_median`, `_avg`, `_min`, `_max`, `github_repos_owner_unique`;
- по ним построятся графики динамики;
- включится поиск аномалий: выбросы (в том числе внутри групп по `owner`),
  невозможные значения, дубликаты, дрейф схемы, резкие изменения записей;
- источник появится во всех вкладках приложения.

Без `mapping` вложенный JSON разворачивается сам: `{"owner": {"login": "acme"}}`
превращается в колонку `owner.login`, списки — в строку через `;`.

Команды: `--list-sources` (проверить), `--only my_source` (собрать только его,
зависимости подтянутся).

## Обход лимита пагинации

Эндпоинты вроде `listing_apartments` отдают все лоты региона, но упираются в
стандартный лимит окна пагинации Elasticsearch (обычно `from + size ≤ 10 000`).
Наивный постраничный обход всегда останавливается примерно на 10 000 записях,
хотя в регионе их кратно больше.

Решение — дробить запрос по значению поля:

```json
"split_param": "filter[housing_complex_id][]",
"split_values_from": "housing_complexes",
"split_values_field": "id",
"concurrency": 8
```

Запрос разобьётся по значениям и пойдёт параллельно через `asyncio`+`aiohttp`.
На одно значение приходится максимум несколько сотен записей, и потолок не
достигается.

Контроль полноты: перед сбором делается один дешёвый запрос за общим числом,
в конце итог сверяется с ним. Расхождение обычно означает, что часть записей
привязана к значениям вне справочника.

### Диагностика: «собрано в разы меньше, чем должно быть»

Почти всегда причина в `split_param` — параметр фильтра оказался не тем, что
ожидает API. **Это ловится за секунды, а не за минуты**: перед тем как дробить
запрос на тысячи, сборщик проверяет `split_param` на 5 реальных значениях.
Если все 5 провалились — сбор источника останавливается, а в консоль и в
`redcat_scraper.log` печатается настоящее тело ответа API (не просто код
ошибки), где обычно прямо написано, какой параметр не распознан.

Что пробовать по очереди, перезапуская
`python redcat_scraper.py --only apartments` после каждой правки:

- `"filter[housing_complex_id][]"` — массив значений (частый вариант для
  Laravel / Spatie QueryBuilder);
- `"filter[housing_complex_id]"` — простое скалярное значение;
- `"filter[housing_complex.id]"` — через точку, как обращение к связанной таблице;
- `"housing_complex_id"` — без обёртки `filter[...]`.

Если не подошёл ни один — скорее всего, у этого эндпоинта нет фильтрации по
ЖК, и дробить нужно по другому полю (диапазон цены, тип объекта, дата).
Списки поддерживаемых `filter[...]` редко публикуют в общей документации —
в этом случае имеет смысл спросить у поддержки API напрямую.

Если видите HTTP 429 — превышен лимит частоты. Уменьшите `concurrency`
у источника или запустите с `--concurrency 2`.

## Форматы выгрузки (почему не Excel)

Excel на десятках тысяч строк открывается минутами, виснет на фильтрах, а лист
ограничен 1 048 576 строками. Замеры на 46 500 записях:

| Формат  | Запись   | Размер   | Чтение/запрос |
|---------|----------|----------|---------------|
| Parquet | 0.17 с   | 2.5 МБ   | 0.04 с        |
| SQLite  | 0.57 с   | 12.5 МБ  | 0.04 с (SQL)  |
| Excel   | 11.04 с  | 4.5 МБ   | 8.41 с        |

По умолчанию пишутся:

- **`reports/redcat_data.db`** — SQLite со всеми таблицами и индексами.
  Открывается в DB Browser for SQLite, подключается к Power BI и Excel через
  Power Query (данные остаются в БД), читается из pandas. С ним же работает
  приложение.
- **`reports/*_<timestamp>.parquet`** — колоночный формат со сжатием. Без
  `pyarrow` автоматически пишется CSV.

Excel доступен флагом `--excel`, но листы больше 200 000 строк обрезаются
(полные данные всегда есть в SQLite/Parquet), о чём выводится предупреждение.

```python
import pandas as pd, sqlite3

df = pd.read_parquet("reports/apartments_20260916_0718.parquet")

con = sqlite3.connect("reports/redcat_data.db")
pd.read_sql("""
    SELECT developer_name, COUNT(*) AS lots, AVG(price / total_area) AS avg_sqm
    FROM apartments WHERE total_area > 0
    GROUP BY developer_name ORDER BY lots DESC
""", con)
```

## История запусков и поиск аномалий

Каждый запуск пишет строку метрик в `history/run_stats.db` и пересобирает
`reports/dashboard.html` — самодостаточный HTML с графиками (те же данные
видны в приложении на вкладке «Обзор», в более удобном виде).

Считается всё из фактически собранных данных, без оценок: объём предложения,
полнота сбора в %, цены (среднее, медиана, края), цена за м², оборот лотов,
длительность сбора.

**Поиск аномалий** работает на двух уровнях и ничего не знает про недвижимость.

*По истории запусков:* резкие скачки любой метрики (модифицированный z-score
на медиане и MAD), изменение более 35% за запуск, падение полноты сбора,
залипшая метрика (не менялась 4 запуска подряд, хотя раньше менялась — признак
кэша на стороне API).

*По данным запуска:* выбросы в числовых полях глобально и внутри групп,
невозможные значения (`positive_fields`), пустые обязательные поля, дубликаты
идентификаторов, резкое изменение значения у конкретной записи, исчезновение
целой группы, дрейф схемы (новое или пропавшее поле, падение заполненности,
смена типа).

Важная деталь: запуски, помеченные как неполные, исключаются из базы
сравнения. Иначе недогруз из-за сети задаёт ложную норму и маскирует
настоящие аномалии.

Настройки: `--sensitivity 2.5` (строже), `--no-anomalies` (выключить),
`--fail-on-critical` (код выхода 2 — для планировщика и CI).

### История значений по каждой записи

В `history/run_stats.db` копится таблица `record_history`: значение каждого
числового поля каждой записи на каждом запуске. Снапшот помнит только прошлый
запуск, а здесь остаётся весь ряд — график цены одного лота за полгода виден
прямо в карточке записи. Хранятся последние 30 запусков
(`REDCAT_KEEP_HISTORY_RUNS` в `.env`).

## Если что-то не работает

**«Не удалось запустить приложение»** — проверьте `python --version`.
Приложению не нужны сторонние библиотеки, только сам Python.

**«Для сбора данных не хватает библиотек»** — `pip install -r requirements.txt`.
Сообщение перечисляет все недостающие пакеты сразу, а просмотр уже собранных
данных при этом продолжает работать.

**Порт 8765 занят** — приложение само возьмёт следующий свободный и напишет
адрес в консоли. Либо укажите свой: `python studio.py --port 9000`.

**Поиск ничего не находит** — нажмите «Перестроить индекс» на вкладке «Поиск».
Индекс не обновляется сам после сбора, чтобы не замедлять каждый запуск.

**Правки пропали** — проверьте, что файл `studio.db` на месте. Он и есть ваша
рабочая копия правок; при переносе приложения его нужно копировать вместе
с остальным.

**Данных нет вообще** — либо запустите сбор, либо `demo_data.bat`, чтобы
посмотреть интерфейс на выдуманном наборе.

**Собралось меньше, чем должно** — `python redcat_scraper.py --diagnose`.
Проверка займёт секунды и покажет, на каком именно шаге теряются записи.
